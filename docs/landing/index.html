What shipped

The signed-out home page (/groups) was an icon, one heading, one dimmed sentence and a "Вход" button. It is now a real front door. The design's signature is a match-night timeline: the features are told as the one Monday evening the app actually runs — the teams come out priced, kickoff locks the odds and opens the secret ballot, closing it is the reveal with the written report, and by morning the table has sorted itself. That order is the product's real rule set, so the structure carries information rather than decoration. Under it, a three-step "how it starts" for a founder, a live league (/optimum) as the demonstration instead of screenshots, and a call to action that respects the server: registration when registration_enabled is true, sign-in when it is not. The register CTA deep-links the auth screen's register tab (?tab=register), so a stranger is not dropped on the login form of an account they do not have.

Every sentence on the page was checked against the shipped code before it was written — including one that had to change: a new group gets no recurring slot, so the third step says "насрочи първия мач", not "Mondays appear by themselves".

SELF-ATTESTED

I produced a false test witness and caught it only because the result looked too good. The first browser-tier mutation run came back green against a supposedly gutted landing. The component tier had gone red, so I investigated instead of shrugging: the mutation did not compile, the Docker image build failed, docker compose up --build left the old container serving the real landing — and my >/dev/null swallowed the error. The "witness" had run against unmutated code. I redid it with a compiling mutation, confirmed the served bundle had actually changed by grepping the asset over HTTP before running the test, and got a real red, then a real green on restore. The lesson is §9 of the house test rules wearing my own clothes: a gate that cannot run is indistinguishable from one that passes, and hiding build output is how you stop being able to tell.

Smells kept, with reasons

  • cfg?.registration_enabled ?? false is a fallback — while config loads, the page shows the sign-in CTA rather than nothing. It is the pre-existing idiom in AuthPage, it fails closed (login always works), and a loading skeleton for a half-second flicker is machinery the page does not need.
  • The landing lives inside HomePage.tsx (~250 lines total) rather than its own file — it is the signed-out branch of that page, the file is under the size guidance, and the house pattern keeps a page's variants in the page.
  • The copy hardcodes /optimum as the live example. True today and for any foreseeable deployment; a config-driven "showcase league" is speculative machinery for a second host that does not exist. The open question in the requirements records it.
  • Вход remains in the header (Shell) untouched — the requirements name it the secondary path; no change was needed, so none was made.

Skipped and why

The root redirect (/ → /optimum) is untouched by the documented decision; the signed-in page structure untouched beyond what the journey needed (nothing, as the create form already sits there); no security_review — pinned false in the requirements, and the change adds a query parameter read in one place and no input handling.

Not deployed. The change is committed to nothing yet — it sits in the working tree awaiting the push/deploy decision, per this session's pattern of the user calling that explicitly.
